# RazorRisk Production Dataset

## Production data plane

RazorRisk no longer treats the checked-in SQLite file as the application dataset. The production dataset lives in **PostgreSQL**, which can be:

- the included Docker PostgreSQL service for reproducible local/staging deployments, or
- a managed PostgreSQL provider such as **Supabase** for a persistent, multi-replica deployment.

The application connects through `DATABASE_URL`; no transaction data is stored in the container filesystem.

## Dataset source

The repository uses a **reproducible synthetic payment-fraud dataset** generated by `data/generate_synthetic_data.py`. It intentionally contains:

- normal users, devices, IPs and merchants
- benign IP co-locations
- device-sharing fraud rings
- proxy/IP clusters
- high-velocity carding
- suspicious-merchant collusion
- device-cycling/structuring
- legitimate hostel/family look-alike communities
- fraud ground-truth labels for offline evaluation

Default startup seed: **1,500 users / 12,000 transactions / seed 42**.

The generator writes directly to the configured PostgreSQL database, so the dataset is available to every API replica and worker.

## Production ingestion

For a real deployment, point `DATABASE_URL` at the managed PostgreSQL instance and run:

```bash
python -m data.generate_synthetic_data
```

or let the API seed an empty database during first startup.

For the existing real-data ingestion experiment, see `data/ingest_real_kaggle_dataset.py`. The application schema remains the canonical storage model so the ML feature pipeline does not depend on a local file.

## Why PostgreSQL

SQLite is excellent for deterministic unit tests and small local experiments but a single `.db` file is not an appropriate shared write store for horizontally scaled API/worker replicas. PostgreSQL provides concurrent transactional writes, indexes, foreign keys and a network-accessible shared data plane.

## Migrating an existing v23/v25 SQLite database

If you already have a local `razor_risk.db` whose data must be retained, use the one-time migration helper instead of copying the file into production:

```bash
python data/migrate_sqlite_to_postgres.py ./razor_risk.db \
  --database-url "$DATABASE_URL"
```

The script creates the PostgreSQL schema and inserts rows with conflict-safe semantics. Back up the source database before migration.
